# 技术决策记录

## D1：SQLite 绑定改为 node:sqlite（替代 better-sqlite3）——已验证

- 原方案：better-sqlite3（AI 建议，需验证）。
- 验证发现：better-sqlite3 v12.11.1 与 v13.2.0 的 GitHub Releases 均无 Electron 45（ABI 150）win32-x64 预编译产物；本机编译需完整 MSVC 工具链，打包与维护成本高。
- 决定：改用 Electron 45 内置 Node 24 的 node:sqlite（通过 process.getBuiltinModule 加载），无原生模块、无需 rebuild、打包简单。
- 代价：node:sqlite 在 Node 中标记为 experimental；已把全部访问封装在 src/main/db.ts 一层，未来 API 变化只改这一层。
- 验证证据：单元测试 5 条（含关闭重开持久化）；打包应用启动后创建 thesis-workbench.db（28672 字节）。

## D2：渲染层用 Vite SPA，主进程用 tsup

- 桌面应用加载本地静态文件（loadFile），不需要 Next 服务端；旧项目 standalone 打包的复杂度（node_modules 拷贝、本地端口服务）不再存在。

## D3：规避打包器剥离 node: 前缀

- 现象：esbuild/tsup 将 node:sqlite 改写为裸 specifier "sqlite"，Electron 运行时无法解析（Cannot find module 'sqlite'）。
- 解决：db.ts 用 process.getBuiltinModule("node:sqlite") 运行时加载，源代码中不保留该模块说明符。
- 验证证据：打包前定位到 main.js 中 require("sqlite") 报错；改为 getBuiltinModule 后 electron 测试与打包应用均通过。

## D4：带材料进入的阶段初始化

- 已有材料 → 建议起始阶段：初稿→写作；数据→分析；文献→文献整理；题目→研究设计；无材料→选题。
- 中间阶段自动标记「跳过（已有材料）」，建立项目阶段标「完成」，建议阶段标「进行中」；跳过可恢复。
- 依据：《产品与技术方案》4 节（支持从已有材料进入、不强制从头开始）与 AC02。

## D5：模板未实现方法的处理

- 依据：方案 5 节与 AC17 / AC19。

## D7：保存模型改为「立即发送 + 请求跟踪」（替代 500ms 防抖）

- 原实现的问题：防抖窗口内关闭会丢内容；按字段名区分的定时器跨阶段/项目可能冲突；旧请求可能清掉新请求的完成记录；保存失败时一直显示「保存中」。
- 新实现：每次变更立即通过 IPC 发送（主进程按序同步写入 SQLite；消息发出后即使窗口立刻关闭，写入仍会完成）；用 pendingRef/failedRef 跟踪未完成与失败请求；响应仅在仍处于同一阶段与项目时更新界面，避免旧响应污染新状态；保存失败显示「保存失败 + 重试」；beforeunload 在存在未完成或失败写入时提示。
- 验证：shell + templates 两个 Electron 端到端测试通过（含填写→切换阶段返回→内容仍在、重启恢复）。

## D8：阶段 2 —— 模型服务配置与密钥存储

- 密钥：safeStorage（Windows DPAPI）加密后仅存密文（base64）入库；渲染层永远拿不到明文，只有「已配置」状态；空密钥不覆盖旧值。
- 网络：undici 实现，直连 / EnvHttpProxyAgent（系统代理）/ ProxyAgent（自定义代理）；请求用 AbortSignal 支持取消。
- 连接测试三层：鉴权（/models）→ 模型可用（最小请求 max_tokens=1）→ 实际能力（真实小任务）；任一层失败即停止；取消用 testId → AbortController。
- 五角色（检索辅助 / 研究设计 / 写作 / 分析解释 / 审阅）独立分配服务商与模型，存 role_assignments 表。
- 验证：本地模拟 OpenAI 兼容服务端到端（三层通过、401 鉴权失败、慢响应取消、重启后配置/密钥状态/角色持久化）；单测 19 条。真实 Key 联网验证待用户提供。

## D9：阶段 3 —— 真实文献链路

- 真实数据源适配器：Crossref（书目检索 + DOI 核验）、arXiv（Atom XML，用 fast-xml-parser 解析）、PubMed（E-utilities JSON）。均为免费无密钥接口；测试环境可用 TWB_CROSSREF_BASE / TWB_ARXIV_BASE / TWB_PUBMED_BASE 指向本地模拟服务。
- 数据模型：literature_items（含 source / verified_status / verified_note / fulltext_status / preprint 字段）、evidence_cards（观点 + 原文定位）、search_log（真实检索式、来源、时间、状态）。
- 核验语义：真实数据源保存的题录自动标「已核验」；手动录入、RIS/BibTeX 导入默认「待核验」；人工核验显式记录说明；同 DOI / 同标题去重且保留原记录（来源冲突不覆盖、不由模型裁定）。
- PDF 关联只复制文件并记录文件名，不解析全文、不生成页码；国内平台只提供官方入口 + 可复制检索式 + 人工核验记录，不虚构 API。
- AI 只用于生成检索式（检索辅助角色），不产出文献记录。
- 验证：单测 26 条；文献 e2e（模拟服务）覆盖完整链路；真实调用：Crossref DOI 核验返回真实题录、arXiv/PubMed 各返回 10 条真实结果；Crossref 书目检索在验证时段 HTTP 429（如实上报，未伪造）。发布前需把 Crossref 的 mailto 占位邮箱换成真实联系邮箱。

### D9 补充：Crossref 429 的根因与修复

- 现象：书目检索（/works?query...）持续返回 HTTP 429（空响应体），而 DOI 端点（/works/{doi}）正常。
- 根因：mailto 使用占位邮箱 research@example.com。Crossref 会拒绝示例域名的邮箱（HTTP 429），真实邮箱才进入「礼貌池」获得正常检索配额。已用对照实验证实（example.com → 429；真实邮箱 → 200）。
- 修复：设置页「搜索服务」标签新增「联系邮箱（Crossref 礼貌池）」字段，存 app_settings 表；检索时随请求携带。代码中不再假设固定邮箱。
- 验证：用户真实邮箱（3161594975@qq.com）经应用完整路径（设置保存 → 文献阶段检索 "deep learning"）返回 10 条真实题录（HTTP 200）。该邮箱只存在用户本机数据库，不进代码与 Git。

## D10：阶段 4 —— 选题、研究设计与开题

- AI 只生成草稿与框架：选题方向、设计字段草稿、假设卡片、开题章节均标记「AI 生成」，需人工复核。
- 反编造机制：候选方向的依据只能引用本项目文献库条目（按序号校验），引用列表之外的索引一律丢弃并标「来源待核验」；设计草稿只允许写入真实模板字段（未知字段丢弃）；空输入时模型被明确要求写「待核验」而不是编造（真实验证中 DeepSeek 对空设计输入如实返回「待核验」，未编造研究问题）。
- 假设卡片结构化存储（编号/陈述/IV/DV/依据），问卷方法专用，不强制中介、调节变量。
- 版本管理：设计/开题阶段保存内容快照（字段 + 假设/章节 JSON），恢复旧版本只写回内容并提示下游复核，不删除旧版本。
- 验证：单测 29 条；electron e2e 5/5（模拟模型 + 模拟 Crossref）；真实 DeepSeek：候选方向 5 条（含数据路径/可行性/限制，依据诚实标注）、开题框架 5 章节。打包版启动正常。

## D11：推理型模型（deepseek-v4-pro）支持

- 现象：deepseek-v4-pro 是推理型模型——思考过程在 choices[].message.reasoning_content，最终答案在 content；max_tokens 不足时 content 为空或数组被截断（finish_reason=length），导致「模型未返回有效候选方向」。
- 修复 1：chat() 在 content 为空时回退读取 reasoning_content。
- 修复 2：extractJson 增加截断容错——逐个解析数组中已完成的 {…} 对象，丢弃未完成的尾元素。
- 修复 3：阶段 4 调用的 max_tokens 从 2000 提升到 8000（推理预算），单请求超时 180s。
- 效果（真实验证）：deepseek-v4-pro 生成的候选方向含具体数据路径/可行性/限制；研究设计起草给出具体研究问题、构念与 4 条假设卡片（依据如实标「理论推导，待核验」）；开题框架 5 章节。保守性消失，反编造标注保留。

## D12：写作管线（全流程论文 RAG）落地

- 来源：用户提供的 Python RAG 骨架（docs/rag-pipeline-reference/）移植为 TypeScript。
- 系统提示词逐字保留（「正文/引用/gap」约束不变）：接地而非编造、写出而非回避、禁止「待核验」占位、缺料进 gaps。
- 检索层替换：原版 Chroma + sentence-transformers 嵌入 → 改为应用文献库的确定性精准检索（拉丁词 + 中文二字滑窗；标题 3.0×、题录 1.4×、摘要 1.0×、证据卡片 1.6× 加权；证据卡片带原文定位）。理由：知识库即文献库（数十条规模），确定性检索可解释、可复现、无嵌入漂移，且证据卡片提供「原文定位」级精度。测试环境可用 mock 服务，无需新增 Python 依赖。
- LLMClient：按用户自定义 API 实现——应用设置页配置的服务商 + 「写作」角色模型（deepseek-v4-pro），temperature 0.4，max_tokens 8000，240s 超时；密钥 safeStorage 加密。
- 反编造：引用编号 [@ref_N] 只映射材料清单中的真实来源；正文中出现清单外编号时 UI 明确告警；检索无命中时退回最新入库的真实文献。
- 真实验证（deepseek-v4-pro + 真实文献 Nature 2015 Deep learning + 证据卡片）：正文 3 段全部句子带 [@ref_1] 真实引用；无「待核验/需进一步验证」占位；缺口 1 条（发展脉络缺文献，给出补料建议）。防御性/保守性消失，防编造保留。
